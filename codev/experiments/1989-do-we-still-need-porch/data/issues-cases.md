# Experiment 1989: GitHub issues that mention porch, classified

## 1. Population

- Queries (repo `cluesmith/codev`, read-only, run 2026-11-26):
  - `gh issue list -R cluesmith/codev --search porch --state all --limit 1000 --json number,title,state,body,createdAt,closedAt,labels` → 311 issues
  - `gh issue list -R cluesmith/codev --label area/porch --state all --limit 1000 --json …` → 47 issues, all already in the search result
  - Fix PRs: GraphQL `closedByPullRequestsReferences` plus the `ClosedEvent` closer for every issue, and any PR the body or comments name as the fix.
- Union: **311 issues** (150 open, 161 closed), matching `porch_issues.json`.
- Created 2026-01-29 to 2026-11-26.
- Method: every body read in full, in five batches (one by me, four by forked readers given the same written rules). `gh issue view N --comments` was read where the body left the bucket unclear. All five batches were then reconciled to the same rules (section 7). Every quote in section 3 was checked mechanically as an exact substring of the issue body.
- Rules: notes.md "Approach: counting rules", plus the bucket rules in the task. One bucket per issue, precedence gate-incident > save > defect > feature > incidental.

### The same defect filed more than once

The defect count above counts issues. These clusters are one underlying defect, or one mechanism, filed several times. Counted once per cluster, the 96 defect issues are **78 distinct defects**.

- `--help` on a porch subcommand runs the subcommand and changes state: #1259, #1539, #1762
- verify task hard-codes 'Step 1: Merge the PR' for a pre-merge verify phase: #1791, #1863
- a failed check's output is truncated and the failing test is never named: #1801, #1853
- state writes push to `origin`, which fails for fork contributors: #1230, #1258
- post-merge bookkeeping commits strand on the merged branch and never reach main: #802, #1229, #1367, #1446, #1732
- check timeout kills only the direct child; a surviving grandchild hangs `porch done`: #1706, #1752
- status.yaml resolved from the wrong worktree copy; approvals land on another lane's branch: #1235, #1593, #1703
- plan phases snapshotted into status.yaml once; no way to re-scope after a plan change: #954, #1135, #1900
- a consult that did not run (skip stub or no verdict) is scored as an approving COMMENT: #1166, #1656
- porch's state commits move the open PR's head and restart CI: #1462, #1733, #1873
- porch is passive at phase boundaries; builders drift ahead or idle (same evening's lanes): #1295, #1298

## 5. What these issues cannot show

- **Saves are close to invisible in issues.** An issue gets filed when something goes wrong and someone decides to write it up. A porch refusal that worked (a check holding a phase for a real defect, "VERIFICATION REQUIRED", a gate holding a builder that would have moved on) leaves no issue behind. Zero saves here is a fact about what gets filed, not a measurement of how often porch stopped things. The status files, rebuttal files and builder threads are the sources that can show saves.
- **Incidents never filed.** Only reported problems appear. Costs that builders absorbed silently (extra turns, a retried check, a hand-run command) appear only when someone wrote them up. Gate passes nobody noticed cannot appear at all; all five gate-incidents were caught after the fact by a human or a builder.
- **Labels date only from 2026-05-19.** `area/porch` (47 issues) and every other `area/*` label start on 2026-05-19. Before that, porch issues are found only by the word "porch" (GitHub search matches title, body and comments). An issue about porch that never uses the word is missed in any month.
- **Reporting changed over time.** From about 2026-07 onward many defects are field reports from adopter workspaces, filed by architects at their owner's direction, often with "field evidence" from one day. The monthly counts (defects: Feb 11, Mar 4, Apr 3, May 8, Jun 5, Jul 19, Aug 12, Sep 16, Oct 9, Nov 9) track that reporting practice as much as porch's quality.
- **One issue is not one incident.** Some issues record a single run. Others record a rate: #1229 found 106 of 179 projects on `main` stranded mid-phase, #1759 found 810 dead pending gates, #1793 found 7 of 8 phases force-advanced. Others record a class seen three times in a morning. The counts here are issues, with duplicate clusters noted. They are not event counts.
- **Observed or code-read is the issue's own claim.** Nothing here was reproduced. "Human intervened" is marked only where the body or comments say so, so 39 defects are "not stated", not "no".
- **Open/closed is not fixed/unfixed.** #919 and #1295 closed without a fix. Fix PRs come only from GitHub closing references and PRs named in the issue. A fix that landed without `Fixes #N` is not linked.
- **No cost in time or tokens.** Issues rarely say how long a wedge lasted or what it cost, so porch's running cost cannot be read from them.
- **Nothing about soft mode.** Issues cannot say whether a builder without porch would have made the same mistakes or caught the same ones. Many costs counted here (wrong worktree resolution, stranded commits, CI churn from state commits) exist only because porch exists. Others (a review loop cut short, a check that can never fail) are failures of a guard that soft mode would not have at all.
- **Bodies are as of 2026-11-26.** Some were rescoped after filing (for example #1543 and #1911). The quotes are from the current body.

## 7. Classification decisions (applied to all five batches)

- **Precedence:** gate-incident > save > defect > feature > incidental. An actual gate pass or skip without a human is a gate-incident, whoever did it. A gate that only *could* be bypassed is a defect.
- **Defect** means porch's own behaviour: porch CLI code and state, porch's own task text, `protocol.json` content porch executes (checks, ceilings, lane lists), and phase prompts porch delivers whose text misdescribes porch or fails to deliver a template. A design flaw with concrete reported harm counts (for example CI churn from state commits). A missing capability that wedged a real project counts as C-wedge (#1297, #1538, #1670, #1900).
- **Incidental, with a tag (not costs to porch):**
  - consumer surfaces misreading correct porch state (`F6-consumer`);
  - role docs and skills contradicting each other (`prompt-docs`);
  - protocol prose or templates wrong in a way a soft-mode builder reading the same text would also hit (`protocol-content`);
  - spawn's builder-prompt (`spawn-prompt`);
  - a porch check failing because of a flaky or slow test or the environment (`check-friction`);
  - porch's own test suite (`porch-test`);
  - consult-lane output bugs, unless the issue is about porch's handling of that output.
- **Changed during reconciliation:**
  - #411 defect → incidental (check-friction).
  - #685 and #742 defect → incidental (protocol-content).
  - #738 defect → incidental (spawn-prompt).
  - #619 kept as a defect, re-pinned to its porch item (the fragile `has_phases_json` check).
  - #562, #777 and #1013 tagged.
- **Borderline calls a reader may want to flip:**
  - #1543: a gate-incident on one historical table row.
  - #1272: the gate was skipped, not approved.
  - #1541: the main fault is the forge script; only the porch task text is porch's.
  - #1011 and #1279: phase-prompt template delivery.
  - #1892: a lack of concurrency control, counted as C-check.
  - #1902: a mixed sweep, counted for its phase-prompt items.
  - #887: could be read as a protocol design change.
  - #1306, #1531, #1641 and #1360: consult faults that left porch's review phase blocked, kept incidental.

Flipping all of them moves at most about 10 issues between buckets. It does not change the zero in the saves bucket.
