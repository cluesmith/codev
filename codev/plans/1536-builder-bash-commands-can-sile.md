# PIR Plan: Extend the #1018 worktree guard to Bash

## Understanding

Issue #1018 built a structural guard against a builder silently writing into the **main checkout** instead of its own worktree: `.claude/hooks/worktree-write-guard.cjs`, installed at every spawn, denies any absolute `Write`/`Edit`/`MultiEdit` path that resolves outside the worktree root. The guard is generated by `packages/codev/src/agent-farm/utils/worktree-write-guard.ts` — the `WORKTREE_WRITE_GUARD_SCRIPT` string constant (the emitted `.cjs`) plus `buildWorktreeGuardFiles()` (emits `.claude/settings.local.json` wiring the hook on the matcher `Write|Edit|MultiEdit`).

The gap: **Bash is unguarded**. `cd <main-checkout>/apps/<pkg> && npx jest` runs against main's copy untouched. Because the worktree is byte-identical to main at the branch base and its path is only the main path plus a low-salience `.builders/<id>/` segment, dropping that segment is an easy, silent error. The failure is self-concealing: main's copy runs without error but yields plausible-but-wrong results (missing suites, stale behavior) that imitate flaky tooling. Confirmed recurring (issue comments: ≥2 occurrences in 3 days across workspaces). Reads and executions against the wrong tree are exactly the uncovered half of the #1018 threat model.

The fix is to extend the same guard to `Bash`: add `Bash` to the PreToolUse matcher, and in the hook scan the command string for absolute paths that land in the main checkout but outside the worktree, denying with a teaching message. Fail-open on any error is preserved.

### Settled direction (per architect, not open design)

Add `Bash` to the matcher; scan the command against the two roots the guard derives (the worktree root and its `.builders`-parent = the main checkout); keep the fail-open contract; make the deny message teach. **The one open design decision for the plan-approval gate is the escape-hatch shape** — see "Escape hatch (the gate decision)" below.

### Explicitly out of scope

The cwd-instability observation in the issue body ("shell cwd sometimes persists, sometimes resets") is recorded context, not this lane. This plan does not investigate or change harness cwd behavior.

## Proposed Change

All logic stays in the single source of truth, `worktree-write-guard.ts` (the emitted `.cjs` string + the settings builder). No new files.

### 1. Wire Bash into the matcher

In `buildWorktreeGuardFiles()`, change the matcher from `'Write|Edit|MultiEdit'` to `'Write|Edit|MultiEdit|Bash'` (`worktree-write-guard.ts:222`). One hook command serves both tool families; the emitted `.cjs` branches on `tool_name`.

### 2. Derive the main-checkout root in the hook

The hook already canonicalizes the worktree `root` (baked-in `CODEV_WORKTREE_ROOT`, else `git rev-parse --show-toplevel`). The main checkout is that root with its trailing `/.builders/<id>` removed — i.e. split the worktree path at the last `/.builders/` segment and take the prefix. This is cheap and deterministic. If the worktree path contains no `.builders` segment (unexpected), we cannot derive a main root → **fail open** for Bash (nothing to compare against).

### 3. Scan Bash commands

For `tool_name === 'Bash'`, read `tool_input.command` (a string; missing/non-string → allow). Tokenize the command on shell whitespace/operators and, for each **absolute** token, apply this order (the lexical check must come **first**):

1. **Lexical worktree check (allow):** normalize the token *lexically only* (`path.normalize`, no `realpath`) and, if it `isInside` the worktree root (compared as-written against the baked/normalized worktree path), allow it and move on. This is load-bearing: every worktree contains spawn-created symlinks into the main checkout (`.env`, `.codev/config.json`, and any `worktree.symlinks` entries), so a legitimate worktree-absolute reference like `cat <worktree>/.env` would *canonicalize into the main root*. Checking the as-written token against the worktree root first means those references are allowed without ever being realpath'd.
2. **Canonicalize + main-root check (deny):** only tokens that are lexically *outside* the worktree proceed. Canonicalize the token (reusing `canonicalize()`); if it equals the main root or `isInside` the main root, **deny** (the trap: a main-checkout path outside the worktree, e.g. bare `cd <main>` or `<main>/apps/x`).
3. Otherwise → ignore (system paths like `/usr/bin/node`, `/tmp`, `$HOME/...`, and all relative paths are untouched).

This differs deliberately from the Write/Edit path, which canonicalizes first (resolving symlinks there is **correct** — writing through a link into main mutates main's file, so a Write to `<worktree>/.env` *should* deny). The lexical-first order applies to Bash only.

Only paths under the main checkout are candidates, so ordinary absolute references outside the repo entirely are never blocked. Relative paths are never touched — `cwd` is the worktree, so they resolve correctly by construction. The scan is a heuristic over a shell string (quoting/`$()`/spaces-in-paths are not fully parsed); any parse surprise falls through to allow, consistent with the fail-open contract. The check is deliberately narrow (main-checkout-rooted only) to keep false positives near zero.

### 4. Teaching deny message

Name the offending path, state both roots, explain the silent-wrong-tree consequence, and give the fix. Draft:

> Blocked: `<path>` is in the main checkout (`<mainRoot>`) but outside this builder's worktree (`<worktreeRoot>`). A path that drops the `.builders/<id>/` segment silently reads/runs against main's copy and yields plausible-but-wrong results (missing suites, stale behavior). Use a relative path (cwd is your worktree) or re-root under `<worktreeRoot>`.

(The final clause depends on the escape-hatch decision below.)

### Escape hatch (the gate decision)

How does a builder deliberately reference the main checkout from Bash when legitimately needed? Three options, with failure modes:

**Option A — Sticky env toggle** (e.g. `CODEV_ALLOW_MAIN_CHECKOUT=1` in the session env; hook allows when set).
- *Failure mode (disqualifying):* it is **sticky**. Once exported in the session it disables the Bash guard for every subsequent command silently — reintroducing exactly the self-concealing hole this issue closes. A model that hits the deny may `export` it reflexively and never see the guard again. This is the anti-pattern the issue warns about.

**Option B — Per-command sentinel (RECOMMENDED).** The builder includes an explicit marker in the single command, e.g. a comment `# codev:allow-main-checkout`. The hook receives the whole command string; if the marker is present, it allows that one call and nothing else.
- *Why:* scoped to exactly one command — the next command is guarded again. The deliberate act is **loud** (visible in the command and the transcript) and auditable; the accidental main-checkout path is still blocked. Matches the issue's "narrow, explicit escape hatch … a deliberate act stays possible while the accidental one becomes loud."
- *Form:* a **sentinel comment** rather than an inline env assignment (`VAR=1 cmd`). Inline env binds only to the first simple command in a `&&`/pipeline chain, so it is ambiguous for compound commands; a comment the hook greps for anywhere in the string is unambiguous and works regardless of command shape.
- *Failure mode & mitigation:* a model could learn to prepend the marker reflexively after a deny. Mitigation: the deny message does **not** hand over the marker verbatim; it teaches "use a relative or worktree-absolute path" and mentions only that a deliberate main-checkout reference has a documented override in the builder role doc. Because the marker is per-command and shows up in the transcript, any reflexive use is visible and self-limiting — unlike the sticky toggle.

**Option C — No hatch at all.** Simplest, most robust against model self-defeat (nothing to invoke).
- *Failure mode:* a genuine, rare need to reference the main checkout from Bash becomes impossible (fail-open covers only *errors*, not correct denies); the builder must route around it (a git ref-based diff from inside the worktree usually suffices). Acceptable as a strict fallback and a one-line reduction from B (just skip the marker check).

**Recommendation: Option B (sentinel comment).** It preserves the visible-failure bound this class needs while keeping a deliberate, auditable, per-command override. If the reviewer prefers maximum strictness, C is a clean fallback.

### 5. Role-doc prose (explanation stays; enforcement is new)

Update the "Worktree discipline" bullet in **both** `codev/roles/builder.md` and `codev-skeleton/roles/builder.md` (byte-identical section, lines ~97–100) so it notes the guard now covers Bash reads/executions too, and — if Option B is chosen — documents the sentinel-comment override in one line. Prose remains explanation; the hook is the enforcement.

## Risks & Alternatives Considered

- **Risk — false positive blocks a legit command.** Mitigated by scoping the scan to main-checkout-rooted absolute paths only (system/tmp/home/relative paths are never candidates) and by the per-command escape hatch. Fail-open on any parse surprise means the worst case is today's unguarded behavior, never a bricked command.
- **Risk — heuristic shell parsing misses an obfuscated path** (quotes, `$()`, spaces-in-paths). Accepted: the guard targets the *common accidental* form (`cd <main>/… && …`), not an adversary. Misses fall through to allow (fail-open), matching #1018's contract.
- **Risk — worktree symlinks into main false-positive the Bash scan.** Real: every worktree has spawn-created symlinks (`.env`, `.codev/config.json`, `worktree.symlinks`) whose realpath is in main. Mitigated by the lexical-first order (step 3.1) — a worktree-absolute token is allowed on its as-written form before any `realpath`. Write/Edit deliberately keep canonicalize-first, since writing through such a link mutates main's file and *should* be denied. Both directions are covered by tests.
- **Risk — the escape hatch gets used reflexively.** Addressed by choosing the per-command (non-sticky) form and by not advertising the marker in the deny message (Option B rationale).
- **Alternative — full shell AST parse.** Rejected: heavy, still imperfect, and violates the "self-contained, Node-core-only, no deps" constraint of the emitted `.cjs`.
- **Alternative — guard by cwd instead of scanning the command.** Rejected: the trap is an absolute path *inside* an otherwise correct command; the harness cwd is already the worktree, so cwd alone cannot catch `cd <main>/…`.
- **Note — my own session cannot self-verify via live hooks.** This builder's live guard was installed from the *installed* package at spawn, not from the source being edited; editing the source changes nothing about my session. Verification is by pipe-testing the emitted `.cjs` with synthetic hook-input JSON and by the vitest suite (below) — never by triggering my own hooks. (I am a builder subject to the exact trap I am fixing; my own verification commands stay relative or worktree-absolute.)

## Test Plan

- **Unit (vitest), the primary bar** — extend `worktree-write-guard.test.ts` (it spawns the *exact* emitted `.cjs` with fixture stdin, so it tests what builders get):
  - Bash deny: `cd <main>/apps/x && npx jest`; bare `cd <main>`.
  - Bash allow: worktree-absolute (`cd <worktree>/apps/x`); relative (`npx jest`); system path (`/usr/bin/node`); `/tmp` reference; escape-hatch marker present (Option B); fail-open when worktree root unresolved.
  - **Symlink regression (the architect-flagged false-positive):** a fixture symlink inside the worktree that points into the main checkout (e.g. `<worktree>/.env` → `<main>/.env`); Bash `cat <worktree>/.env` **allows** (lexical-first), while `Write` to that same `<worktree>/.env` still **denies** (canonicalize-first — writing through the link mutates main).
  - Deny reason contains both `<mainRoot>` and `<worktreeRoot>`.
  - Matcher assertions include `Bash`.
  - Run from the worktree: `cd packages/codev && npx vitest run src/__tests__/worktree-write-guard.test.ts src/agent-farm/__tests__/harness.test.ts` (worktree-relative — no main-checkout path).
- **Manual pipe-test of the emitted `.cjs`** (the architect-noted correct method): write `WORKTREE_WRITE_GUARD_SCRIPT` to a temp `.cjs`, pipe synthetic `{tool_name:"Bash", tool_input:{command:"…"}, cwd:"…"}` JSON with `CODEV_WORKTREE_ROOT` set, and confirm deny/allow/fail-open for each root and the error path. (Temp file under the scratchpad, not a main-checkout path.)
- **Build/type gate:** `pnpm --filter @cluesmith/codev build` and `check-types` from the worktree (tsc, not just vitest) before dev-approval.
- **CMAP consultation** after the code and after the tests, per protocol.
- No cross-platform/mobile surface; this is a Node hook. The existing suite already guards macOS `/tmp` symlink normalization and Linux literal-path behavior via `FIXTURE_HOME`.
